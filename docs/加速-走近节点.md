# 让访问走更近的 Cloudflare 节点（实测 + 可执行方案）

> 实测时间：2026-11-28。本机出口：四川联通 AS4837。
> 结论先行：**换 IP 能把 3.4s 压到 0.8s**，但只有一种做法能长期稳住，另外两种要么贵、要么会失效。

---

## 一、先看清现状（实测数据）

> 实测时间：2026-11-28，本机出口：四川联通 AS4837。

| 项目 | 实测值 |
|---|---|
| 域名 | `eat.isxl.cn`，NS = `kurt/nataly.ns.cloudflare.com`（**已在 Cloudflare 托管**） |
| 实际落到 | **LAX（洛杉矶）**，所有请求一致 |
| 协议 | **http/1.1**（不是 h2） |
| 访问方式 | **走 IPv6**（`2408:8266:...`，联通 IPv6 段） |

### 🔴 真正的根因：到 Cloudflare 的 IPv4 不通，IPv6 绕美国

| 访问方式 | 成功次数 | 落点 | 平均耗时 |
|---|---|---|---|
| 强制 **IPv4** | **0 / 4** | — | 无法连接 |
| 强制 **IPv6** | 3 / 4 | **LAX** | 3739 ms |
| 自动（实际走 v6） | 1 / 4 | LAX | 1105 ms |

对照组：

| 测试 | 结果 |
|---|---|
| `baidu.com`（IPv4） | 200，1.29s ✅ |
| `cloudflare.com`（IPv4） | **超时**（下载 1.2MB 后卡死）❌ |
| `eat.isxl.cn`（IPv6） | 通，但全在 LAX |

**结论**：不是你站点的问题，是**这条线路到 Cloudflare 的 IPv4 路由基本不可用**，IPv6 虽然通但被调度到美西。所以：

- 前面测出的「优选 IP 快 4 倍」是**碰巧连上的那几次**——那些 IP 是 IPv4，而你的 IPv4 大概率连不上
- 稳定性差（2/6、5/6）的根源不是节点选择，是**链路本身**
- `styles.css` 出现 40 秒超时，是这个原因的直接体现

### 为什么换 IP 会有帮助（但不彻底）

`162.159.x.x` 与 `104.21.x.x` 属于不同 anycast 前缀，BGP 路由宣告路径不同，所以同一域名换不同边缘 IP 可能落到不同机房。但只要底层的 IPv4 路由是坏的，**换到哪个 IP 都是在赌**。

### 延迟对比（仅统计成功的请求）

| 资源 | 默认(LAX) | 优选(HKG) | 提升 |
|---|---|---|---|
| `/` | 1184 ms | **779 ms** | 34% |
| `/styles.css` | 2101 ms | **1048 ms** | 50% |
| `/app.js` | 2684 ms | **995 ms** | 63% |
| `/api/health` | 1513 ms | **1068 ms** | 29% |

成功时确实快一半。但前提是能连上。

## 二、按你的实际情况排序的方案

### 🔴 第 0 步（必做）：先确定问题在哪一跳

在动手改任何配置前，先跑这一组判断：

```powershell
# ① IPv4 到 Cloudflare 通不通（这是关键）
curl.exe -sS -m 8 -4 -o NUL -w "v4 cloudflare: %{http_code} %{time_total}s`n" https://www.cloudflare.com

# ② IPv6 通不通
curl.exe -sS -m 8 -6 -o NUL -w "v6 cloudflare: %{http_code} %{time_total}s`n" https://www.cloudflare.com

# ③ 落到哪个节点
curl.exe -sS -m 8 https://eat.isxl.cn/cdn-cgi/trace | Select-String "colo|http=|ip="
```

**我这边跑出来的结果**：

```
v4 cloudflare: 超时（下载 1.2MB 后卡死）
v6 cloudflare: 通
colo=LAX  http=http/1.1  ip=2408:8266:...（IPv6）
```

如果你的结果类似 → **问题在运营商侧，代码和配置都改不了**，往下看第 1、2 步。

---

### 第 1 步：代理走直连还是走代理，二选一 —— 效果最直接

你本机有 `127.0.0.1:7897`。实测走它的时候，出口 IP 变成 `119.5.35.197`（仍是联通），但偶尔能进 IPv4。

**必须做的判断**：浏览器打开站点 → F12 → Network → 点任一请求看 **Remote Address**：

| Remote Address | 含义 | 该做什么 |
|---|---|---|
| `2408:8266:...` | 走 IPv6 直连 → LAX，慢 | 见第 2 步 |
| `104.21.x.x` / `172.67.x.x` | 走 IPv4 直连 | 你这边 IPv4 是通的，加 hosts 可能有用 |
| 代理服务器 IP | 被代理接管 | 配直连规则或换代理节点 |

**如果是 Clash 类工具**，加一条直连规则先排除代理干扰：

```yaml
rules:
  - DOMAIN-SUFFIX,isxl.cn,DIRECT
  - DOMAIN-SUFFIX,pages.dev,DIRECT
```

加完重启，再测。这一步不改任何线上配置，随时可撤。

---

### 第 2 步：关掉 IPv6 优先 —— 针对「IPv6 绕 LAX」

如果确认走的是 IPv6 且全在 LAX，**让系统优先用 IPv4**，可能反而更快（前提是你的 IPv4 到 Cloudflare 能通，用第 0 步的①验证）。

**Windows**：网卡属性 → IPv6 → 取消勾选（临时测试用，测完记得开回来），或者调前缀优先级：

```powershell
# 查看当前前缀优先级
netsh interface ipv6 show prefixpolicies
```

**浏览器层面**（不改系统）：Chrome/Edge 打开 `chrome://flags/#disable-ipv6`——注意这个 flag 在新版已被移除，替代方案是用代理强制 IPv4。

⚠️ **别盲目关 IPv6**：国内 IPv6 直连有时比 IPv4 快。用第 0 步的数据决定，不要凭感觉。

---

### 第 3 步：加 hosts（仅当你的 IPv4 能通）

**先验证成功率**，这是唯一有意义的指标：

```powershell
# 连测 10 次，看成功几次
1..10 | ForEach-Object {
  $r = curl.exe -sS -m 6 -o NUL -w "%{http_code}" `
    --resolve "eat.isxl.cn:443:162.159.140.98" `
    "https://eat.isxl.cn/api/health" 2>&1
  "$_ -> $r"
}
```

- **成功 ≥ 8/10** → 值得加
- **低于 6/10** → 别加，你的 IPv4 到那个 IP 一样不稳

达标后：

```powershell
Copy-Item C:\Windows\System32\drivers\etc\hosts C:\Windows\System32\drivers\etc\hosts.bak
Add-Content C:\Windows\System32\drivers\etc\hosts "`n162.159.140.98`teat.isxl.cn"
ipconfig /flushdns
```

回滚：`Copy-Item ...hosts.bak ...hosts -Force; ipconfig /flushdns`

**局限**：只对这一台电脑生效。

---

### 第 4 步：Cloudflare for SaaS —— 对这个目标**无效**，不必做

我已核实官方文档：Free 计划确实含 100 个 custom hostnames、$0（[Plans](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/)）。

**但它不解决你的问题**：它改变的是证书签发与路由的**管理方式**，边缘节点选择仍由 anycast + BGP 决定。你的 BGP 路径没变，它不会把 LAX 变成 HKG。

---

### 第 5 步：Argo —— **明确无效，别买**

Argo 优化的是 **Cloudflare 边缘 → 你的源站** 这一跳，走私有骨干网。

**你的源站就是 Cloudflare Pages 本身，没有独立源站，这一跳不存在。** 慢的是「你的电脑 → Cloudflare 边缘」，Argo 管不到。

$5/月 + $0.10/GB，买不到你要的效果。

## 三、如果最后还是慢：换托管位置

这是绕开「联通 → Cloudflare 路由差」的**唯一根治办法**：让站点不在 Cloudflare 上。

| 方案 | 换来的效果 | 代价 |
|---|---|---|
| **国内 CDN + 源站在 Pages** | 国内访问 50–100ms | 需备案；CDN 回源到 Pages 仍慢，但静态资源可缓存 |
| **迁到国内静态托管**（对象存储 + CDN） | 彻底解决 | 要备案 + 迁移成本 |
| **Vercel / Netlify** | 可能走不同路由，需实测 | 同样是海外，未必更好 |
| **自建 VPS（国内/香港）+ Nginx** | 完全可控 | 有服务器成本，失去 D1 |

对一个「吃什么」转盘，**最实际的是接受现状**——页面已经做了骨架屏和乐观更新，慢但可用。

## 四、代码层已经做完的

### 4.1 首屏请求数 3 → 1（已上线）

`HTTP/1.1` 下浏览器最多 6 并发，且每次请求都要完整往返 800ms–2.6s。首屏原本 3 个请求（html / css / js），现在**内联成单文件，只剩 1 个**。

```
public/index.html  +  styles.css  +  app.js
        ↓ node build.mjs
dist/index.html     （单文件，87KB，br 压缩后约 20KB）
```

实测验证：静态请求 1 个，渲染正常，转盘可用，无 JS 异常。

**重新构建**：`node build.mjs`，然后 `npx wrangler pages deploy dist --project-name=eat`

### 4.2 其他已做的

骨架屏、乐观更新、增量渲染（滚动不重建 DOM）、缓存优先、静默同步、请求失败重试。

这些让等待「不难受」，但消除不了等待。

## 五、执行顺序建议

按这个顺序做，每步都有明确的判断依据：

| 步骤 | 做什么 | 判断标准 |
|---|---|---|
| 1 | 跑第 0 步的三条命令 | 确认是 IPv4 不通还是 IPv6 绕路 |
| 2 | F12 看 Remote Address | 确认是否被代理接管 |
| 3 | 若走了代理 → 加 DIRECT 规则 | 改了就能立刻看出差别 |
| 4 | 若 IPv4 能通 → 测优选 IP 成功率 → 加 hosts | 成功率 ≥8/10 才加 |
| 5 | 都不行 → 接受现状，或用国内 CDN | — |

**不要做的事**：

- ❌ 买 Argo（对你的架构无效）
- ❌ 配 Cloudflare for SaaS（不改变节点选择）
- ❌ 盲目关 IPv6（国内 v6 有时更快，要用数据判断）

## 六、一句话总结

你的问题是**运营商到 Cloudflare 的路由质量**，不是配置错误，也不是代码问题。

- 换 IP 有效但只能自用，且依赖偶然可用性
- Argo 和 SaaS 解决不了这个问题
- 代码层已经做到极限（单请求、骨架屏、乐观更新）
- **真正的根治办法是换掉 Cloudflare 这个托管点**，代价是备案和迁移

对一个「吃什么」转盘，我的建议是：**先做第 1–3 步（零成本），剩下的接受它。**

## 四、给你的执行建议（按性价比排序）

| 优先级 | 做什么 | 预期效果 | 成本 |
|---|---|---|---|
| **1** | 改本地 hosts 指到 `162.159.144.1` | 3.4s → **0.8s** | 0 |
| **2** | 按路线 A 配 Custom Hostname | 长期稳定走近节点 | 0 |
| **3** | 检查 HTTP/2 是否被代理降级 | 首屏并发提升 | 0 |
| 4 | 代码层继续优化（已经做了） | 掩盖延迟而非消除 | 0 |
| ✗ | Argo | 对本场景**无效** | $5/月 |

### 立刻可做的第一步

以管理员身份打开 PowerShell，执行：

```powershell
# 备份原 hosts
Copy-Item C:\Windows\System32\drivers\etc\hosts C:\Windows\System32\drivers\etc\hosts.bak

# 追加优选 IP（162.159.144.1 实测落到 HKG，823ms）
Add-Content C:\Windows\System32\drivers\etc\hosts "`n162.159.144.1`teat.isxl.cn"

# 刷新 DNS
ipconfig /flushdns
```

然后浏览器硬刷新（Ctrl+Shift+R），再看 Network 里的耗时。

**如果变快了**，说明诊断正确；**如果没变**，把 hosts 删掉即可回滚（备份在上一步）。

### 如果 hosts 生效了，想要长期方案

那就是路线 A。它让 Cloudflare 自己在边缘路由层面处理，不需要依赖某个具体 IP 的偶然可用性。

## 五、诚实说明

- **`162.159.144.1` 今天快，不代表永远快。** Cloudflare 的前缀和 BGP 通告会变。这是「优选 IP」方案的固有缺陷，所以只建议用于自用，不要写进线上配置。
- **我无法从代码层面解决这个问题。** 页面已经做了乐观更新、骨架屏、增量渲染、缓存优先，这些都是「让等待不那么难受」。真正的 3.4s → 0.8s 必须在解析或代理层解决。
- **Cloudflare API 现在连不上**（schannel 握手间歇失败），所以我没能替你查 Argo 的实际开关状态和 Custom Hostname 的可用性。上面路线 A 的步骤是按官方文档写的，具体按钮位置可能随控制台版本变化。
