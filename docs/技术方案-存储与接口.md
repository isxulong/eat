# 转盘随机抽取工具 · 存储与读写接口技术方案

> 状态：待确认
> 仓库：`github.com/isxulong/eat`（当前仅 `main` + `.gitignore`，空白起步）
> 部署目标：GitHub 托管源码 → Cloudflare 发布

---

## 1 需求拆解与硬约束

| 需求 | 隐含的技术约束 |
| --- | --- |
| 前端为静态页面 | 不能有自建服务器/常驻进程；一切动态能力必须落在 Cloudflare 的 serverless 上 |
| 通过 GitHub 托管、Cloudflare 部署 | 可用 Pages（Git 集成）或 Workers（含 Static Assets / Builds） |
| 前端手动增删改选项 | 需要浏览器可直接调用的写接口 + 交互式编辑界面 |
| 后台集中批量处理 | 需要「脚本/管理端一次提交多条」的原子批量接口，不能只有单条 CRUD |
| 修改后台持久保存，刷新/重访仍生效 | 唯一真源必须在服务端存储；`localStorage` 只能当缓存或离线草稿 |
| 选项多时录入要快 | 需要批量粘贴解析、去重、虚拟滚动，而不是一行一行点「添加」 |

**关键推论**：只要「静态页面 + 服务端持久化」，就必然存在一个服务端写入口。而这个页面是公开的，所以写入口必须鉴权——否则任何人都能把转盘清空。

## 2 候选方案对比（6 条路线）

### A. 纯前端 localStorage / IndexedDB
- 写入：浏览器本地。
- 致命点：**不满足「后台持久保存」**——换设备、换浏览器、清缓存即丢；「后台集中批量处理」无从谈起（没有后台）。仅能作为离线草稿层。

### B. GitHub 仓库 JSON + 浏览器直连 Contents API（PAT 写在前端）
- 存储：仓库里一个 `data/options.json`，每次保存 = 一次 commit。
- 致命点：**PAT 打在前端 JS 里等于公开**（看一眼源码就能拿到仓库写权限）；每次增删改都产生一个 commit，历史被灌成垃圾；并发保存靠文件 SHA，撞车直接 409；GitHub API 从浏览器调用还有 CORS 与 5000 次/小时限额。
- 唯一优势：数据天然在 git 里，可读、可回滚、可人工在 GitHub 网页上改。

### C. GitHub 仓库 JSON + Pages Function 代理（PAT 只在服务端）
- 存储：同上，但令牌藏在 Function 的 Secret 里，前端只调自家 `/api/*`。
- 优点：**零新增云资源**（不需要 D1/KV/Supabase），完全跑在已有的仓库 + Pages 上；「后台批量处理」可以退化为直接编辑仓库里的 JSON 并 commit。
- 现实缺陷：
  1. 每次保存一个 commit → 高频编辑把提交历史撑爆（前端用户每改一个字就是一条）；
  2. 写延迟 0.8–2s（GitHub API + commit），体验明显差于数据库；
  3. 并发写只能靠 `sha` 乐观锁，冲突后整个文件重写；
  4. 免费账号 API 5000 次/小时，批量脚本容易撞限；
  5. 没有查询能力，只能整文件读写 → 选项上千后每次读写都是全量 JSON。
- 定位：**在拿不到 Cloudflare 数据库权限时的最佳降级方案**，不是首选。

### D. Cloudflare KV
- 优点：接入最简单，读极快且便宜（免费 10 万读/天），配 Pages Functions 一行代码。
- 缺陷：
  1. **最终一致，全球生效最长 60s**——用户改完刷新可能看不到自己的修改，直接违反「刷新后仍生效」的体感要求；
  2. 免费额度**写只有 1000 次/天**，批量导入或高频编辑很容易撞墙；
  3. 没有部分更新与事务：只能整块 read-modify-write，两个人同时编辑必丢更新（后写覆盖先写）；
  4. 无查询、无排序能力，全靠应用层。
- 定位：**适合做只读缓存层**（把 D1 的整份快照放 KV 里加速），不适合当真源。

### E. Cloudflare D1（SQLite）
- 优点：
  1. **真正的行级存储 + 事务**：`db.batch()` 是一个 SQL 事务，批量增删改要么全成要么全不成；
  2. **按行并发安全**：改一条只写一行，两个人改不同选项互不影响；
  3. 免费额度极宽：**500 万行读/天、10 万行写/天、5GB**（2026-09 起超限才报错，日常用量差两个数量级）；
  4. 与 Pages Functions 一等公民集成（`env.DB` 绑定），本地 `wrangler pages dev --d1` 可离线开发；
  5. 原生 SQL → 批量脚本、导入导出、统计、按标签筛选都不用写额外逻辑。
- 缺陷：单主区（非多区读写，读走主区，亚洲访问 ~100–300ms）；需要建库 + 执行 schema + 绑定，比 KV 多两步；超免费额度会直接拒绝查询（可监控，本项目量级不会触发）。

### F. Durable Objects（SQLite 后端）
- 优点：单写者强一致，天然适合「一份共享列表 + 多人同时编辑」，还能挂 WebSocket 做实时同步。
- 缺陷：Pages 里不能定义 DO 类，必须**另建一个 Worker** 再绑过来；免费额度按请求/时长计（10 万请求/天、13 万 GB-s/天）；对一个转盘工具属于明显过度设计。

### G. 第三方 BaaS（Supabase / Firebase）
- 优点：自带鉴权、实时订阅、控制台可视化编辑。
- 缺陷：引入第二个云厂商与第二套密钥（`.env` 管理、CORS 白名单）；数据离开 Cloudflare；免费实例有休眠/冷启动；与「Cloudflare 部署」的目标不一致。

### 对比矩阵

| 方案 | 持久化真源 | 并发安全 | 批量原子性 | 免费额度余量 | 写延迟 | 额外资源 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A localStorage | 否 | — | — | — | 0ms | 无 | 仅作草稿层 |
| B 仓库直连 | 是 | 差（sha 冲突） | 靠整文件重写 | 5000 次/h | 0.8–2s | 无 | 否决（令牌泄漏） |
| C 仓库代理 | 是 | 差 | 整文件重写 | 5000 次/h | 0.8–2s | 无 | 降级备选 |
| D KV | 是 | 差（无事务） | 无 | 写 1000/天 | 20–80ms | KV 命名空间 | 只做缓存 |
| **E D1** | **是** | **好（行级）** | **好（事务）** | **写 10 万/天** | 100–300ms | D1 库 | **推荐** |
| F DO | 是 | 最好 | 好 | 中 | 50–150ms | 额外 Worker | 过度设计 |
| G Supabase | 是 | 好 | 好 | 中 | 100–400ms | 第二厂商 | 引入外部依赖 |

## 3 推荐方案

**Cloudflare Pages（Git 集成）+ Pages Functions + D1（唯一真源）+ localStorage（离线草稿/首屏缓存）+ 可选 KV/边缘缓存（读加速）**

选择理由，按重要性排序：

1. **只有 D1 同时满足「持久」「并发不丢数据」「批量原子」三条硬要求**。批量全量替换（后台集中处理的核心动作）必须是一个事务，KV 和仓库 JSON 都是整块覆盖，中途失败就变成半截数据。
2. **写入额度够用两个数量级**。按 200 个选项、50 人日活估算：读 ≈ 250 次/天 × 200 行 = 5 万行/天（上限 500 万），写 ≈ 几百行/天（上限 10 万）。不存在因用量被迫升级付费的风险。
3. **行级更新让「前端单人编辑」和「后台批量导入」可以同时进行**，靠 `revision` 乐观锁把冲突显式暴露成 409，而不是静默覆盖。
4. **它是 Cloudflare 官方推荐的新项目存储路径**，未来加多转盘、分组、权重、历史记录都只是加表，不换架构。
5. **本地可全离线开发**：`wrangler pages dev public --d1 DB=local` 一条命令跑起来，不依赖线上账号就能验证全部接口。

代价（明确接受）：需要一次性的建库/绑定/执行 schema 三个动作；单主区带来的 100–300ms 读延迟，用「客户端 stale-while-revalidate + 边缘缓存 10s」压到体感无感。

## 4 数据模型

```sql
-- 转盘（当前单转盘，预留多转盘）
CREATE TABLE IF NOT EXISTS wheels (
  id          TEXT PRIMARY KEY,
  title       TEXT    NOT NULL DEFAULT '今天吃什么',
  revision    INTEGER NOT NULL DEFAULT 1,   -- 乐观锁版本号，每次写 +1
  updated_at  INTEGER NOT NULL
);

-- 选项
CREATE TABLE IF NOT EXISTS options (
  id          TEXT    PRIMARY KEY,          -- 客户端生成 UUID，天然幂等
  wheel_id    TEXT    NOT NULL,
  text        TEXT    NOT NULL,
  weight      REAL    NOT NULL DEFAULT 1,   -- 权重，默认等概率
  disabled    INTEGER NOT NULL DEFAULT 0,   -- 软删除/临时停用，保住 id 便于撤销
  sort        INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_options_wheel ON options(wheel_id, sort);

CREATE TABLE IF NOT EXISTS meta (
  k TEXT PRIMARY KEY,
  v TEXT NOT NULL
);
```

设计要点：
- **id 由客户端生成（UUID v4）** → 重试/重复点击不会产生重复行（`INSERT ... ON CONFLICT(id) DO UPDATE`），网络抖动不需要服务端去重。
- `disabled` 软删除 → 批量误删可一条 SQL 恢复；真正清理走后台任务。
- `sort` 整数列 → 拖拽排序只改一行。
- `revision` 放在 `wheels` 上而不是选项上 → 一次校验覆盖整份列表的一致性。

## 5 接口契约

统一前缀 `/api`，响应 `application/json`，错误体 `{ "error": "code", "message": "..." }`。

| 方法 | 路径 | 用途 | 鉴权 | 幂等 |
| --- | --- | --- | --- | --- |
| GET | `/api/wheel` | 取整份列表快照（含 revision） | 公开 | 是 |
| POST | `/api/options` | 新增一条或多条（粘贴批量时一次提交） | 写权限 | 是（按 id） |
| PATCH | `/api/options/:id` | 改文本/权重/停用 | 写权限 | 是 |
| DELETE | `/api/options/:id` | 删除（物理或软删） | 写权限 | 是 |
| POST | `/api/options/batch` | **后台集中批量处理**：一次提交 add/update/remove，单事务 | 写权限 | 是 |
| POST | `/api/wheel/import` | 全量替换（`mode=replace`）或追加（`mode=append`） | 写权限 | 否（需带 revision） |
| GET | `/api/export` | 导出 JSON/纯文本，供备份与外部批处理 | 公开或写权限 | 是 |
| GET | `/api/health` | 部署自检（DB 可达、schema 版本） | 公开 | 是 |

### 契约细节

**GET /api/wheel**
```json
{ "revision": 42, "title": "今天吃什么",
  "options": [ { "id": "u_8f3a…", "text": "麻辣烫", "weight": 1, "disabled": 0, "sort": 0 } ] }
```
响应头 `Cache-Control: public, max-age=10, stale-while-revalidate=60`。10 秒窗口内边缘直接返回，写操作后客户端主动重新拉取，不存在看到旧数据的窗口。

**POST /api/options**
```json
{ "texts": ["麻辣烫", "兰州拉面"], "expectedRevision": 42 }
```
`expectedRevision` 省略则不校验（快速添加场景）；带上则冲突返回 409。

**POST /api/options/batch（后台批量核心）**
```json
{ "add":    [ { "id": "u_xxx", "text": "黄焖鸡" } ],
  "update": [ { "id": "u_yyy", "text": "沙县小吃", "weight": 2 } ],
  "remove": [ "u_zzz" ],
  "expectedRevision": 42 }
```
实现：拼成一个 `env.DB.batch([...])`，SQLite 保证原子性；成功返回 `{ "revision": 43, "applied": { "added": 1, "updated": 1, "removed": 1 } }`。

**冲突语义**：所有写接口比对 `expectedRevision` 与当前 `revision`，不一致返回
```json
HTTP 409 { "error": "revision_conflict", "revision": 43, "options": [ …最新快照… ] }
```
客户端拿到 409 直接用返回的快照重绘并保留本地未提交的编辑，而不是弹「保存失败」让用户重来。

**鉴权**：写接口要求 `Authorization: Bearer <token>`，服务端用与 `ADMIN_TOKEN` 的定长比较（时间安全），失败 401。前端编辑模式由「口令 → 换取短期会话 token（2h，HttpOnly Cookie）」获得，口令本身不进 localStorage、不进代码、不进 git。

**限流/体积**：单次 `texts` ≤ 2000 条、payload ≤ 256KB（超限 413）；按 IP 的写频率上限（如 30 次/分钟，429），挡住脚本刷写。

## 6 「选项多」的录入体验设计

这是需求里单独点出来的痛点，方案落到交互层：

1. **一次粘贴即批量导入**：大文本框，自动按 `换行 / 逗号 / 顿号 / 分号 / 制表符` 切分，去首尾空白、去空行、**按文本去重**（大小写与全半角归一化后比较），实时显示「识别到 137 条，去重后 132 条」，一键入库 → 一次 `/api/options` 请求。
2. **拖入文件**：`.txt / .csv` 直接拖到页面，走同一套解析管线。
3. **快速连加**：单行输入框，Enter 即加并保持焦点，适合边想边加；输入框上方实时显示已添加条数。
4. **列表虚拟滚动 + 即时搜索**：上千条也不卡，搜索框支持包含匹配，批量勾选后一次删除/停用/启用。
5. **原地编辑**：双击即改，失焦自动保存（PATCH 单行，不重发全量）。
6. **本地草稿保护**：编辑内容随时写进 `localStorage`，接口失败或断网不丢输入；提交成功才清除。这层纯粹是「防丢」，不作为真源。

## 7 部署链路

```
GitHub 仓库 isxulong/eat
  ├─ public/            静态站点（index.html / app.js / styles.css）
  ├─ functions/api/…    Pages Functions（读写接口）
  ├─ schema.sql         D1 建表
  └─ wrangler.toml      D1 绑定 + 兼容性日期
        ↓ git push
Cloudflare Pages（Git 集成，build 命令留空，输出目录 public）
        ↓ 绑定
Cloudflare D1（eat-db）→ 执行 schema.sql → 注入 ADMIN_TOKEN Secret
```

需要的凭据：Cloudflare API Token（`D1:Edit` + `Pages:Edit` + `Account Settings:Read`），用于我这边自动建库、绑项目、跑 schema、首次部署；或者全部由你在控制台点（我给出逐屏步骤）。GitHub 侧已就绪（仓库 + PAT 已配置在本地 remote）。

## 8 降级路线（如果暂时拿不到 Cloudflare 权限）

| 触发条件 | 降级方案 | 代价 |
| --- | --- | --- |
| 无 CF API Token、不想建 D1 | 方案 C：Pages Function 代理 GitHub Contents API，`data/options.json` 当真源 | 每次保存一个 commit、写延迟 1–2s、并发靠 sha |
| 只想先看转盘效果 | 方案 A：纯静态 + localStorage，带 JSON 导入/导出 | 无跨设备持久化，后台批量只能导入导出 |
| 需要多人实时协同 | 升级到 Durable Objects + WebSocket | 多一个 Worker，复杂度上升 |

推荐落地顺序：**先做 P0 静态转盘 + localStorage（半天可用）→ 再接 D1（P1）**，这样 Cloudflare 凭据到位之前页面就能看。

## 9 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 写口令外泄 | 他人可改/清空选项 | 口令只换短期会话 token；写接口限流；保留 `revision` 历史便于回滚；定期换口令 |
| 两人同时批量导入 | 后写覆盖先写 | `expectedRevision` 强制校验 → 409 + 最新快照，前端自动合并提示 |
| 误删大量选项 | 数据丢失 | 默认软删除（`disabled=1`）+ `/api/export` 定时备份到仓库 |
| D1 单区延迟 | 首屏慢 100–300ms | 边缘缓存 10s + 客户端 SWR 缓存，先渲染缓存再静默更新 |
| 免费额度被刷 | 查询被拒 | 写限流 + payload 上限 + `/api/health` 监控；本项目量级余量 20 倍以上 |
| 中国大陆访问质量 | 打开慢 | 绑定自定义域、静态资源走边缘缓存；必要时前端加骨架屏 |

## 10 分阶段实施计划

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 | 静态转盘（Canvas/conic-gradient 扇形、缓动停位、结果高亮）+ local CRUD + 批量粘贴解析 + localStorage | 断网可用，粘贴 100 条一次入库不卡 |
| P1 | D1 + `/api/wheel` `/api/options` `/api/options/batch` + 编辑模式鉴权 + SWR 缓存 | 刷新/换浏览器数据一致；两人同时编辑不同选项不互相覆盖 |
| P2 | 批量控制台（导入/替换/导出/停用恢复）、409 冲突合并、软删除回收站 | 1000 条替换一次事务成功，冲突有明确提示 |
| P3 | 多转盘、分组标签、权重可视化、历史抽取记录 | 可切换多个场景（吃饭/团建/值班） |

## 11 结论（一句话）

**用 D1 做唯一真源、Pages Functions 做写入口、localStorage 只做离线草稿与首屏缓存**；写接口按「单条 CRUD + 单事务批量」两套并行，用 `revision` 乐观锁暴露并发冲突。这套组合在免费额度内能撑到十万级选项与日常多人编辑，且不引入任何第二个云厂商。
